# Поиск по полке сворачивает регистр регулярным выражением, а не `icontains`

Поиск по названию и номеру сравнивает через `iregex` с экранированной строкой поиска, а
не через привычный `icontains`.

Причина в базе. Проект живёт на SQLite, а её `LIKE` — во что `icontains` и превращается —
сворачивает регистр только для ASCII. `'Акт разграничения' LIKE '%акт%'` возвращает 0, а
`'Act' LIKE '%act%'` — 1. То же и с `LOWER`: `LOWER('Акт')` — это `'Акт'`. Все названия в
этом проекте русские и приходят из имён файлов, чей регистр — тот, каким его набрали в
папке управляющей компании. Поиск, чувствительный к регистру, находит документ только
тому, кто уже знает, как тот записан, — то есть ровно тому, кому поиск не нужен.

`iregex` на SQLite — это `re.search` Python, зарегистрированный драйвером Django, на
PostgreSQL — оператор `~*`. Оба сворачивают регистр по всему Юникоду, так что поведение
одинаково и при переезде на PostgreSQL. Введённая строка экранируется `re.escape`: читатель
вводит подстроку, а не шаблон, и «АКТ-12/2024» ищется так, как набран.

Разработчик, который приведёт это «к единообразию» с остальным Django-кодом и заменит
`iregex` на `icontains`, сломает поиск по-русски, не сломав ни одного ASCII-теста.

## Рассмотренные варианты

- **`icontains`** — короче и привычнее, использует те же индексы (то есть никаких: `LIKE
  '%…%'` не использует их и так). Отвергнут: на SQLite не сворачивает регистр для
  кириллицы, а это весь язык данных проекта.
- **Зарегистрировать юникодные `LOWER`/`UPPER` на соединении SQLite** — починило бы регистр
  для всей базы разом. Отвергнуто по двум причинам: `icontains` на SQLite не вызывает ни
  `LOWER`, ни `UPPER` — он полагается на сам `LIKE`, — так что писать `Lower(...)` в
  запросе всё равно пришлось бы; и подмена встроенной функции базы меняет поведение
  `iexact` в аутентификации и в админке, то есть цена решения выходит далеко за пределы
  раздела документов.
- **Хранить нормализованную копию названия и номера в отдельном поле** — дало бы и
  регистр, и индекс. Отвергнуто: миграция и второй экземпляр тех же данных, который надо
  поддерживать в согласии с первым, ради полки в сотни строк, где полный перебор стоит
  миллисекунды.
- **Полнотекстовый поиск** — вне этого этапа: BCMP не читает документ внутри, а близнец
  существует для ИИ-управляющего и не индексируется ([ADR 0007](0007-twin-is-stored-not-produced.md)).

## Последствия

- Поиск идёт полным перебором строк: на SQLite это вызов Python на строку. При сотнях
  документов это незаметно; когда полка вырастет до сотен тысяч, поиск придётся заводить
  заново — и тогда это будет решение о хранилище, а не о лукапе.
- Условие отбора, которое не прочиталось, сужает полку до пустой, а не отбрасывается: адрес
  с чужим `building` отвечает «ничего не нашлось», а не всей полкой. Отброшенное условие
  показало бы читателю его собственную полку целиком, заявив при этом отбор, которого не
  было.
- Отбор применяется после чокпоинта видимости, а не вместо него
  ([ADR 0006](0006-document-visibility-by-own-org.md)): он умеет только убирать строки из
  ответа на вопрос «чьи это документы», и второго места, решающего этот вопрос, не заводит.
