================================================================================
BCMP — конфигурации к изменению: защита входа от перебора паролей
================================================================================

Что уже сделано в коде (коммитить/деплоить как обычно):
  - django-axes[ipware] в pyproject.toml
  - настройки axes в bcmp/settings.py
  - templates/auth/locked_out.html — экран блокировки
  - authentication/views.py — гасит своё сообщение, когда отвечает axes
  - authentication/test_login.py — три теста

Ниже — то, что правится РУКАМИ на сервере (nginx) и один блок в settings.py.

Порядок: (1) nginx, (2) настройки Django, (3) проверка.


================================================================================
1. NGINX — ограничение частоты попыток входа
================================================================================

Зачем, если уже есть axes:
axes считает блокировку по паре (IP, логин). Это сделано намеренно — чтобы
подбор чужого логина не запирал самого сотрудника. Но из-за этого перебор по
СПИСКУ ЛОГИНОВ с одного адреса лимита не достигает: каждому новому логину
достаётся свои пять попыток. Тысяча логинов — пять тысяч проверок пароля, и
каждая стоит одного PBKDF2 в воркере gunicorn. Ограничение по IP в nginx
закрывает именно этот случай и делает это до того, как запрос дойдёт до Python.

--------------------------------------------------------------------------------
1.1. НОВЫЙ ФАЙЛ: /etc/nginx/conf.d/bcmp-limits.conf
--------------------------------------------------------------------------------

Директива limit_req_zone допустима только в блоке http, внутри server она не
работает. Файлы из conf.d/ подключаются в http стандартным nginx.conf — поэтому
отдельный файл, а не правка server-блока.

--- копировать целиком ---------------------------------------------------------

# Счёт ведётся только по POST: у запроса с пустым ключом nginx лимит не считает,
# поэтому открыть и перезагрузить страницу входа можно сколько угодно раз.
map $request_method $bcmp_login_key {
    POST    $binary_remote_addr;
    default "";
}

limit_req_zone $bcmp_login_key zone=bcmp_login:10m rate=20r/m;

# Тот же код, что отдаёт axes, — оба слоя выглядят для клиента одинаково.
limit_req_status 429;

--- конец файла ----------------------------------------------------------------


--------------------------------------------------------------------------------
1.2. ПРАВКА: server-блок somp.stata.kz (443)
--------------------------------------------------------------------------------

Три изменения относительно текущего конфига:

  а) proxy_set_header подняты из `location /` на уровень server.
     ВАЖНО: nginx наследует proxy_set_header в location только если в этом
     location НЕТ ни одного своего proxy_set_header. Оставь их внутри
     `location /` — и новые location для входа будут проксировать без
     X-Real-IP, а axes увидит адрес docker-шлюза вместо клиента. То есть
     ровно на тех запросах, ради которых всё и делается.

  б) добавлены `location = /login/` и `location = /admin/login/` с limit_req.

  в) `listen 443 ssl http2;` -> `listen 443 ssl;` + `http2 on;`
     Старая форма объявлена устаревшей с nginx 1.25.1 и пишет warning при
     каждом reload. ЕСЛИ NGINX СТАРШЕ 1.25.1 — оставить как было
     (`listen 443 ssl http2;`, без строки `http2 on;`).
     Проверить версию: nginx -v

Блок :80 (редирект на https) не трогаем — он в порядке.

--- server-блок целиком, после правок -------------------------------------------

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;

    server_name somp.stata.kz www.somp.stata.kz;

    ssl_certificate /etc/letsencrypt/live/somp.stata.kz/fullchain.pem;      # managed by Certbot
    ssl_certificate_key /etc/letsencrypt/live/somp.stata.kz/privkey.pem;    # managed by Certbot
    include /etc/letsencrypt/options-ssl-nginx.conf;                        # managed by Certbot
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;                          # managed by Certbot

    client_max_body_size 25m;

    # Подняты из location / — наследуются всеми location, которые не объявляют
    # своих заголовков. X-Real-IP nginx перезаписывает поверх присланного
    # клиентом, и это единственный адрес здесь, который нельзя подделать;
    # по нему django-axes отличает клиентов друг от друга.
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_redirect off;

    location /static/ {
        alias /opt/bcmp/staticfiles/;
        access_log off;
        expires 30d;
    }

    location = /login/ {
        limit_req zone=bcmp_login burst=10 nodelay;
        proxy_pass http://127.0.0.1:8000;
    }

    location = /admin/login/ {
        limit_req zone=bcmp_login burst=10 nodelay;
        proxy_pass http://127.0.0.1:8000;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
    }
}

--- конец блока -----------------------------------------------------------------

Про числа: 20r/m + burst=10 nodelay — это десять отправок формы подряд без
задержки, дальше одна раз в три секунды. Человеку, который путается в пароле,
хватает с запасом; скрипт получает потолок в 20 проверок пароля в минуту с
одного адреса вместо тысяч.


--------------------------------------------------------------------------------
1.3. ПРИМЕНИТЬ
--------------------------------------------------------------------------------

    sudo nginx -t && sudo systemctl reload nginx

Сначала именно `nginx -t`: неверно размещённый limit_req_zone роняет конфиг
целиком, а не тихо отключает лимит.


================================================================================
2. DJANGO — настройки, безопасные теперь, когда TLS уже работает
================================================================================

УЖЕ ВНЕСЕНО В КОД (bcmp/settings.py, блок `if not DEBUG:`), руками делать
ничего не нужно — раздел оставлен, чтобы решение было видно:

    # Behind an SSL-terminating reverse proxy (nginx)
    if not DEBUG:
        SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
        AXES_IPWARE_META_PRECEDENCE_ORDER = ('HTTP_X_REAL_IP',)
        SESSION_COOKIE_SECURE = True
        CSRF_COOKIE_SECURE = True
        SECURE_HSTS_SECONDS = 31536000
        SECURE_HSTS_INCLUDE_SUBDOMAINS = True

ОДНО РЕШЕНИЕ ПРИНЯТЬ ДО ДЕПЛОЯ — последняя строка:
HSTS — обязательство на стороне браузера на год вперёд, отозвать его быстро
нельзя. SECURE_HSTS_INCLUDE_SUBDOMAINS распространяет его на ВСЕ поддомены
*.stata.kz, а не только на somp. Если на этом домене есть что-то, что живёт по
http, — эту строку убрать. Сомневаешься — начать с SECURE_HSTS_SECONDS = 3600,
убедиться, что ничего не сломалось, и поднять до 31536000.

SECURE_SSL_REDIRECT сознательно НЕ добавляем: редирект уже делает nginx в блоке
:80, а Django из-за SECURE_PROXY_SSL_HEADER всё равно видит запрос как https.

SECURE_HSTS_PRELOAD тоже НЕ добавляем: попадание в preload-список вшивается в
сборки браузеров, и выйти оттуда — это месяцы. HSTS через заголовок отзывается
за срок max-age, preload — нет.

Отдельно, если решишь ужесточить пароли (не обязательно, влияет на смену пароля
у существующих пользователей) — в AUTH_PASSWORD_VALIDATORS:

    {
        'NAME': 'django.contrib.auth.password_validation.MinimumLengthValidator',
        'OPTIONS': {'min_length': 12},
    },


================================================================================
3. ПРОВЕРКА ПОСЛЕ ДЕПЛОЯ
================================================================================

3.1. Django не ругается на прод-настройки:

    ssh <host> 'cd /opt/bcmp && docker compose exec web python manage.py check --deploy'

    Ожидаемо ровно два предупреждения, оба сознательные:
      W008 SECURE_SSL_REDIRECT — редирект делает nginx;
      W021 SECURE_HSTS_PRELOAD — в preload-список не идём.
    Всё остальное должно быть чисто. Если добавилось W009 — значит
    DJANGO_SECRET_KEY в .env на сервере короткий или дефолтный, заменить на
    длинный случайный.

3.2. axes видит настоящий адрес клиента, а не docker-шлюз.
     Шесть раз ошибиться паролем на https://somp.stata.kz/login/ — на шестой
     должен открыться экран «Слишком много попыток входа» (код 429).
     Затем в логах:

    ssh <host> 'cd /opt/bcmp && docker compose logs --tail=50 web | grep -i axes'

    В строке "AXES: Locking out ..." должен стоять твой настоящий внешний IP.
    Если там 172.x.x.x — значит X-Real-IP до Django не доходит, проверь п. 1.2(а).

3.3. Снять блокировку раньше срока (15 минут), если заблокировал себя:

    ssh <host> 'cd /opt/bcmp && docker compose exec web python manage.py axes_reset'

    Только по одному логину (со всех адресов):
    ... python manage.py axes_reset_username <логин>

    Точно по той паре, на которую и заведена блокировка:
    ... python manage.py axes_reset_ip_username <IP> <логин>

    Посмотреть, кто сейчас заблокирован:
    ... python manage.py axes_list_attempts

3.4. Лимит nginx работает: попытки после ~20 POST в минуту с одного адреса
     должны получать 429 уже от nginx — в access-логе они есть, а в логах
     контейнера соответствующих запросов нет.


================================================================================
ЧЕГО ЭТИ ДВА СЛОЯ НЕ ДЕЛАЮТ
================================================================================

Перебор с распределённой сети адресов (ботнет, ротация прокси) обходит оба:
axes считает по паре (IP, логин), nginx — по IP. Если такое появится, следующий
шаг — не ужесточать лимиты (это бьёт по своим), а двухфакторная аутентификация
для администраторов организаций.
